## Migration lock (A08-05)
`database/migrations.lock.json` lists every migration (version, file name, SHA-256) **in the order it was added**. The SHA-256 is exactly the runner's checksum (`MigrationScript.Checksum`: the script as UTF-8 without a byte-order mark, CRLF turned into LF, upper-case hex), so it is also what `dbo.schema_migration.checksum_sha256` holds on every database. `Hcc.Platform.Tests` `MigrationLockTests` (no database) fails when **(a)** a locked script changed, was removed or renamed (an applied migration is never edited: add a new one), **(b)** a new migration is numbered **below the highest version already in the lock** — on a hotel database that already applied the higher one, the runner would apply it after the later blocks, while a fresh install applies it in number order, so the two schemas can differ — or **(c)** a migration file is not in the lock.
- Adding a migration: give it a number above the highest one in the lock (any free number above it, in or after your block), add it to `Hcc.slnx`, then run `node tools/migrations-lock.mjs --add` (from this folder) and commit the lock with the script. The tool refuses a lower number and never edits an existing entry.
- The entries under `acceptedOutOfOrder` are history: migrations that were merged after higher numbers already existed (0203, 2202, the masters 2800–2871 and 3800, 3100/3101, 3500/3501, 3910–3921). They stay as they are. Only when merging a parallel branch whose lower-numbered migrations have already been applied somewhere (e.g. `main`'s masters 2880/2890/2891 merged after 3951) run `node tools/migrations-lock.mjs --add --accept-out-of-order "<reason>"`, which appends them with that reason. Two branches that each add new, not yet released migrations: keep the lock entries in version order when resolving the merge conflict.

## SQL test harness
- Each SQL test class creates its own database `HccTest_<UTC yyyyMMddHHmmss>_<8 hex>` on `.\SQLEXPRESS` (override: env `HCC_TEST_SQL_SERVER`), applies the migrations and drops it afterwards (`SINGLE_USER WITH ROLLBACK IMMEDIATE`, only names matching that pattern). No other database (e.g. `EtpReporting`) is touched.
- Leftovers after a crashed run: `sqlcmd -S .\SQLEXPRESS -E -C -Q "SELECT name FROM sys.databases WHERE name LIKE 'HccTest[_]%'"`.
- **One-time permission:** the Windows login running the tests needs `dbcreator` on the instance. ## Sign-in and session security (security review 2026-10-26, job S2)

- **Uniform failures (F-M01):** every refused sign-in (unknown name, disabled, no role, wrong credential kind, no credential, wrong secret) answers 403 `BAD_CREDENTIALS` with the same message and costs one PBKDF2 hash at the configured iterations (password 600,000 / PIN 210,000). The precise reason is in the `SIGN_IN_FAILED` audit row only. `DEVICE_NOT_REGISTERED` is checked first, from the device token alone, so it reveals nothing about accounts and no PIN is tried without a registered device.
- **Throttling, no account lockout (F-M02, `SignInThrottle`, settings `Hcc:Access:SignIn*`):** sliding 15-minute window, in memory. Per client address (IPv4, or IPv6 /64): 20 failed sign-ins, then 429 `TOO_MANY_ATTEMPTS` with `Retry-After`. Per (address, sign-in name): 5 failures, then 429 for that pair only. Per name across all addresses: after 5 failures each further attempt is delayed 1, 2, 4 … 8 s (never refused); the server PC itself (loopback without `X-Forwarded-For`) is never delayed. A LAN attacker therefore locks out only their own address, never the Owner. A success clears the pair and the name's delay.
- **Money-role accounts (F-M03):** resetting the password/PIN of, enabling or disabling an account holding any `owner_only_assign` role (OWN, MGR, REC, CSH, ACC, TAD) needs an Owner; a Tech admin manages devices and housekeeping/supervisor/maintenance accounts.
- **Device-bound PIN sessions (F-M07):** a PIN session is accepted only with the `X-HCC-Device` token of the device it was opened on (401 `SESSION_INVALID`, `sessionEnd = DEVICE_MISMATCH`; the session is not ended). Password sessions ignore the header.
- **Health (F-L01):** anonymous `GET /system/health` returns `status` and `serverTimeUtc` only; database name and schema version (and the SQL round trip) only for the server PC or a signed-in user with PERM-ADM-003/005.
- **Retention (F-L03):** `RetentionWorker` purges idempotency records older than 30 days and ended sessions older than 90 days (`Hcc:Access:IdempotencyRetention`, `SessionRetention`). Deposit-link tokens are returned once and never stored in idempotency results.
- **Reveal replays (F-L04)** are audited again; **guest contacts (F-L06)** are masked unless the reader holds PERM-GST-002; **5xx errors (F-L07)** log type, SQL error number and a correlation id (also in the response `details.correlationId` and `X-Correlation-Id`), never the exception message.

## Reopening a closed business day (DEC-077, resolves DEC-028)

Until DEC-077 a closed date was adjustment-only: every correction posted in the open business day. Now the **Owner** can reopen one closed day, correct it and close it again (`Hcc.Domain.Closing.ReopenRules`, `ClosingService`, migrations `3600_closing_day_reopen`, `3601_accounting_tally_export_log`).
- **Reopen:** `POST /commands/ReopenBusinessDay {businessDate, reason}` — PERM-CLS-004 (close.correction.approve, Owner only; the same grant as the DEC-065 cash-book reopen), reason required (≤ 200), audited `BUSINESS_DAY_REOPENED`, outbox `BusinessDayReopened`. Refused (INVALID_TRANSITION) when the day is not closed, when its close has not finished (next day not open), while another day is reopened (**one reopened day per property at a time**), and when the day is locked in Accounting (the Owner unlocks that period first; reopen and `LockAccountingPeriod` take the same per-date application lock).
- **Later days:** reopening day D never reopens later days and leaves their closing records as they are (nothing in the reopen window posts on them). The **current day cannot be closed** until D is closed again (preflight check `reopened`, blocking), so a reopen never outlives the operating day. `GET /closing/business-date` carries `reopenedDate`.
- **While reopened:** a correction (reversal) of a line dated D posts **on D** (`BillingService.DecideApprovalAsync`), and `PostCharge` may name `serviceDate = D` for a missed charge at D's GST rate. Both need an open folio, so an issued **invoice or credit note — number and GST — never changes** (a checked-out stay is corrected with a credit note). Receipts, refunds, deposits, POS and cash entries stay dated the day the money moves (the open day): the drawer is not reopened. Any other earlier date stays DAY_CLOSED. Writers on D hold a shared application lock on D; the re-close takes it exclusively first, so in-flight corrections finish before it reads the day.
- **Cash book (DEC-065):** a reopen does **not** unlock a locked cash-book day and says so in its result; while it is locked, a correction or charge touching D is refused until the Owner runs `ReopenCashBookDay`. The cash-book lock rules are unchanged.
- **Tally:** every Tally export (`GET /accounting/export/tally`) is now recorded (`acc.tally_export`, `acc.tally_export_day`, audit `TALLY_EXPORTED`). Reopening a day that an export carried flags it (`acc.tally_reexport`); every later export carries a flagged day again, even outside the chosen range, with a `RE-EXPORT` note in the XML and lists it in `reexportDates` (A03b-05: its vouchers keep their `REMOTEID`, so importing the file replaces them in Tally; nothing has to be deleted first); while the day is still reopened it is also `PROVISIONAL` and stays flagged; the first export after it is closed again clears the flag. A reopened day counts as **Open** in Accounting (live vouchers, not lockable).
- **Close again:** `RunBusinessDayClose {businessDate: D}` (PERM-CLS-002) re-runs the checks that concern D (pending corrections of D's lines block), derives every figure again from D's records and writes a new closing record (exceptions list each reopen); point-in-time values of the first close stay (deposits held, night audit). The record it replaces is kept unchanged, stamped `superseded_utc` (the only update the snapshot trigger allows); `GET /closing/records` returns `replaced` and `reopens`. Audit `DAY_RECLOSED`, outbox `BusinessDayReclosed`; the business date does not move.

## Rules carried into P1–P7
Command results are JSON objects (records), never bare scalars (`CK_idempotency_result` ISJSON). Authorization: `IAccessPolicy` scope `null` = property-wide only, `AccessScopes.Any` = holds it at any scope (then check the record), `Shift/HkTask/Room` = own/assigned via the owning module's `IAccessScopeResolver`. Money is `long` paise (`Paise`), rounding half away from zero; dates are `DateOnly` / `DATE`, events `DATETIME2(3)` UTC from an injected `TimeProvider`; every command goes through `ICommandRunner` (Idempotency-Key, audit row mandatory, outbox in the same transaction); `XACT_ABORT ON` + `CATCH → ROLLBACK; THROW` in procedures; locked check-then-insert (no catch-duplicate inside a transaction); `expectedVersion` = base64 rowversion → `STALE_VERSION`.
