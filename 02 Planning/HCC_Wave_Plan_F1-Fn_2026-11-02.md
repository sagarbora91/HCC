## 5. Agent economy — keeping usage low

1. **Compact briefs.** A lane brief is ≤ 60 lines: context links (file paths + section numbers, never pasted text), ownership row, forbidden list, definition of done, the exact test commands, DONE-file path, a **turn cap**. The contract carries the detail once; the brief points at sections.
2. **No re-reading of large files.** Lanes read only the contract sections and files named in their brief; HANDOFF / CLAUDE.md / Decision Register are **not** read by lanes (the brief restates the 6–8 rules that matter). The coordinator reads them once per wave.
3. **Graph before grep.** While the knowledge graph is current (refreshed after every wave), lanes answer "where is X" with `/graphify` queries on `graphify-out\` instead of repository-wide greps; a lane greps only inside its own feature folder.
4. **Turn and time caps per lane.** Sonnet module lane: **≤ 60 tool turns / ≈ 2 h**, then write DONE with what is finished and stop. Opus money lane: ≤ 90 turns. Integrator: ≤ 120 turns. A lane that hits the cap does not "try one more thing" — the coordinator decides on a second lane.
5. **Stop-and-report rules.** Stop immediately and write the DONE file when: the contract conflicts with code or a DEC; a Sonnet lane must touch money, GST, a posting, a permission, a setting or `types.ts`; the same test fails twice after a fix; a heavy job returns exit 75 five times in a row (report the queue, do not spin); any file outside the ownership table needs an edit.
6. **No duplicate agents on the same files.** One lane per ownership row; the review lane is read-only; the integrator is the only writer on the wave branch. Never relaunch a lane that has a DONE file — launch a named follow-up lane with the leftover list.
7. **Sonnet reviewers** for UI / exports / docs / tests lanes; Opus reviews only where money moved — and that review is folded into the integrator's merge step, not a separate agent.
8. **Full suites only at the integrator and the gate.** Lanes run their own test project(s) and `npm test` once before DONE (prototype tests are cheap, ≈ 3 min; the server suite is ≈ 25 min and is the integrator's). No lane runs `dotnet test Hcc.slnx`.
9. **Batch size.** Launch a phase as one batch (6–11 agents) so the coordinator's context is spent once; do not trickle single agents. Fewer, fuller lanes beat many thin ones — but never merge a money and a UI lane into one brief.
10. **Coordinator economy.** One Fable coordinator session per wave; it does not read lane worktrees line by line — it reads DONE files and the review files. It writes the contract once; amendments go into a numbered "rulings during the wave" section (as ACC3_Briefs did), not a rewrite.
11. **Re-runs are the real cost.** A FAIL gate re-run is ≈ 1 U; a restarted wave is ≈ 50 % of the wave. Hence: commit every hour, DONE even when unfinished, the ledger file, no launches when the PC is already loaded, the owner is told before any gate so the PC is not restarted during it.
12. **Steps that need the owner's explicit "go" before spending:** launching each wave's lane batch; any gate (≈ 50–70 min of PC time); any emulator session; graphify refresh (≈ 30–60 min CPU); the GitHub push; any Opus lane added beyond the plan's count; any re-run of a whole wave; F7's three-day plan (the most expensive wave) — the owner may choose to run phase B in two batches of 4 on two days to flatten usage.
13. **Weekly budget view.** Before each wave the coordinator states the wave's U and the week's cumulative U; the owner can defer. A week with a gate + a graphify + one XL phase is the limit (≈ 35 % allowance by the owner's own measure).
