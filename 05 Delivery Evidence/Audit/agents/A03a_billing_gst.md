## Rounding sweep

- **Kernel:** `MoneyMath.DivideRoundHalfAwayFromZero` / `PercentOf` / `TaxOf` (`Hcc.Domain/Money/MoneyMath.cs:14-32`). `GstMath.LineTax` and `Split` (`Tax/GstMaster.cs:227-239`). SGST = tax/2 toward zero; CGST takes the rest, so it gets the odd paisa in magnitude. Negative lines are symmetric (e.g. −2223 → −1112 / −1111).
- **Sweep result:** every amount from −200,000 to +200,000 paise at 11 rates (0, 1, 250, 500, 1200, 1800, 2800, 4999, 5000, 9999, 10000 bps), plus 200,000 random amounts up to ±₹10 crore and the edge values. C#: 4,600,044 pairs, 0 tax and 0 split mismatches against `Math.Round(decimal, AwayFromZero)`. Prototype `gst.ts`: 4,600,066 pairs, 0 mismatches against BigInt. The prototype's float arithmetic stays exact up to ₹3,216 crore at 28 %, far above the ₹10 crore field cap.
- **Every place a rate is applied to money in Domain/Application/Infrastructure** goes through the kernel: `BillingService.cs:58, 84, 518`; `BillingPosFolioPort.cs:29`; `GroupCommands.cs:456`; `GroupRules.cs:197, 245, 257`; `CreditNoteRules.cs:78`; `InvoiceRules.cs:52`; `FolioInvoiceSource.cs:73`; `StayRules.cs:135`; `PosRules.cs:47`; `SqlPosStore.cs:847`; `WebBookingRules.cs:101`; `OtaRules.cs:52, 58`; `RateAdjustments.cs:119`; `YieldEngine.cs:25`; `StockRules.cs:57`.
- **`decimal`, `double` and `Math.Round` outside the kernel** (`evidence\A03a\rounding_grep_raw.txt`, 81 lines) are display formatting (`x / 100m` in labels and `Paise.ToString`), percentages and minutes, payroll (A4's area), and `ImportValues.cs:42-55`, which parses rupee text to paise with `decimal` (exact ×100, up to 2 decimals). None of them computes billing money or tax. SQL migrations and stores contain no `ROUND`, `FLOAT`, `DECIMAL` or `MONEY` (grep).
- **Credit notes** recompute tax on the credited part with the same kernel and refuse any cumulative over-credit. That is correct in direction, but it causes A03a-04.

## Invoice-numbering concurrency analysis

- **Allocation** (`SqlInvoiceStore.cs:101-131`): `sp_getapplock` (Exclusive, owner = Transaction, 30 s timeout, resource `ivc.series:{property}:{fy}:{type}`). Then `SELECT … WITH (UPDLOCK, HOLDLOCK)` on `ivc.series`: on first use an INSERT with `last_seq = 1`, otherwise `UPDATE last_seq = last_seq + 1`. All of this runs inside the command's single `ReadCommitted` transaction (`SqlCommandRunner.cs:85-132`), which also writes the invoice, its lines, the audit, the outbox and the idempotency row.
- **Rollback after allocation:** any exception rolls back the whole transaction (`SqlCommandRunner.cs:135-143`). The series increment is undone and the app lock is released, so no number is consumed. This is tested in `InvoiceSqlTests.cs:127-139`: a handler that takes a number and then throws, followed by 8 concurrent issues numbered 1–8 with `last_seq = 8`.
- **Two issuers on one folio:** the folio row is locked first (`FolioInvoiceSource.LoadForIssueAsync` → `LockFolioAsync`), and `UX_ivc_invoice_source` allows one invoice per source. The test confirms one number and the same invoice returned to both callers (`InvoiceSqlTests.cs:152-156`).
- **Database guards:** `TR_series_forward` refuses any change other than +1 and any prefix change (52405); `TR_series_no_delete` (52404); `UQ_ivc_invoice_seq` / `UQ_ivc_invoice_no`; and the immutability triggers 52400–52403, tested in `InvoiceSqlTests.cs:160-181`.
- **Lock order:** issue = folio, then series INV. Credit note = folio (source), then request, then series CRN, then the same folio again (already held). No reversed order exists, so I see no deadlock path. The worst case is a 30 s wait followed by "series busy" (52406).
- **Format:** `{prefix}/{fy}/{seq}` is padded to exactly 16 characters (r.46(b)). The prefix is 1–6 characters (`[A-Z0-9-]`) and is frozen when the FY's series is created. When the series overflows (10,000,000 with "INV") it is refused, never wrapped (probe). Credit notes use the separate prefix "CN" under doc type CRN: `CN/2627/00000001`.
- **Residual gap risk:** none that I found in the code. Gaps in law can still arise outside the app: an invoice the client fails to request after checkout (refusal path `money.ts:226-236`) leaves a departed stay with no invoice. That is a missing document, not a numbering gap.

## taxBps-snapshot check

- `bill.charge.tax_bps` / `tax_paise` are written at posting (`BillingService.cs:57-58, 84, 518`), and the table is append-only (`0400_billing_payments.sql:126-131`). Reversals copy the original's bps and negated tax (`BillingService.cs:340-341`).
- Folio totals recompute tax from each line's stored bps and fail loudly if that disagrees with the stored tax (`FolioStatement.cs:24-27`). Invoices copy the stored bps, tax and split and re-check them (`InvoiceRules.cs:52-62`). The GST resolver is consulted only for new postings (`TaxPorts.cs:16-19`).
- Master changes cannot be backdated (`GstMasterService.cs:38-39`), and a change that is already in force cannot be withdrawn (`:66-67`).
- **Test:** `tests/Hcc.GstIds.Tests/Gst/GstSqlTests.cs:158-180` (`Posted_lines_keep_their_snapshot_after_master_changes_new_postings_use_the_master`) changes laundry to 12 % and the threshold to ₹1,000, then asserts the posted lines and totals are unchanged and new postings use the new rates. It passed in A1's run (GstIds 38/38). I wrote no extra probe.
- **Gap:** the companion snapshot `tax.charge_gst` (category, ITC, split) is not trigger-protected (A03a-09).
