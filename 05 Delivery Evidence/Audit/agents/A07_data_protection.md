## (c) Key management, restore, rotation, retention

**Where the keys live.** `Hcc:GuestIdKeys:{Current, Keys:{id: "dpapi-machine:…"}, Required, AllowMachineScope}` in `C:\Program Files\HCC\Server\appsettings.Production.json`, written by `deployment/windows/New-HccGuestIdKey.ps1:86-96`; the script also `icacls`-restricts the file to SYSTEM, Administrators and `NT SERVICE\HccServer` (`:98-105`) and ACLs its own `.before-guestid-key` safety copy (`:102`). The ring (`DpapiGuestIdKeyRing.cs:17-66`) unwraps with crypt32 DPAPI + fixed entropy `"HCC guest ID key v1"` (`:19`), refuses `plain:` unless `AllowPlainKeys` (`:60-61`), and requires 32 bytes.

**F-M05 follow-up — Fixed.** (1) `HccConfigValidator.ValidateGuestIdKeys` (`HccHosting.cs:123-147`) refuses `AllowPlainKeys`, `plain:` keys, a missing current key, and `dpapi-machine:` unless `AllowMachineScope=true`; (2) `GuestIdKeyFileCheck.EnsureProtected` (`GuestIdKeyFileCheck.cs:66-77`, called at `HccHosting.cs:179-180`) stops the service when anyone other than SYSTEM/Administrators/TrustedInstaller/the service identity can read the settings file, and prints the fixing `icacls` command; (3) `Required=true` (`:132`) refuses to start without the key; (4) `INSTALL.md` §6b now covers generation, offline copy, rotation; (5) `Test-HccDeployment.ps1:251-282` exercises the script (dry run, install, refuse second run, rotate, `Required`/`AllowMachineScope` written). The README's old `dotnet run … guest-id-key new` claim is gone. Residual by design: **a local Administrator (or any SYSTEM process) on the hotel PC can unwrap a `dpapi-machine:` key and, with DB access, read every stored number** (A07-08). The `dpapi-user:` alternative is documented (`INSTALL.md:96`, env-var route `:98`) but impractical for the virtual service account and untested here.

**New machine / Windows reinstall / restore.** A DPAPI blob is bound to the PC (`INSTALL.md:97`; script header `:14-15`). The only recovery is the **offline copy**: the script writes the raw key as base64 in a plain text file on the USB stick (`New-HccGuestIdKey.ps1:81-82`). The documented restore step is "ask your developer to wrap the raw key from the file for the new PC (…`ConvertTo-HccWrappedGuestIdKey`)" (`INSTALL.md:97`): **there is no `-ImportOfflineCopy` switch for the guest-ID key** (the backup key has one: `New-HccBackupKey.ps1:15-20,61-62`), no deployment test for it, and `Restore-HccDrill.ps1` restores the database into a scratch name but **never opens a sealed row**, so a successful drill does not prove the ID numbers are readable (A07-03). A restored backup *is* readable provided the same key id is present in configuration (`SealedGuestId.KeyId` per row, `0601:9`; `Open` fails closed with `UNAVAILABLE` otherwise, `GuestIdProtector.cs:38-40,73-76`). Database backups never contain the key (`Backup-HccDatabase.ps1`: no reference to `GuestIdKeys`; confirmed by grep).

**Rotation.** Documented (`README.md` "Key rotation") and implemented: add a key under a new id (`New-HccGuestIdKey.ps1 -Rotate -KeyId …`, `:17-18,60-63`), set `Current`, restart, then Owner runs `POST /commands/RekeyGuestIds` (PERM-ADM-003 'A'; `GuestIdService.cs:138-160`: row-locked re-seal of every stale row in one transaction, audit `GUEST_ID_REKEY` with counts and key ids only). Test `GuestIdSqlTests.Wrong_key_fails_closed_and_rotation_re_encrypts_under_the_new_key` (`:188-214`). Removing the old key afterwards is manual (README step 3). Images/OCR secrets use the same ring (`SealSecret` carries the key id, `GuestIdProtector.cs:108`) but **`RekeyGuestIds` re-seals only `gst.guest_id_secret`**, not `doc.id_capture.ocr_sealed` / `doc.id_capture_image.sealed` or sealed configuration secrets — after rotation the old key must stay in `Keys` until those rows are purged (A07-07).

**Retention (`documents.retentionDays` 90).** The setting exists (`DocumentRules.cs:18-22`, Master configuration "Data and system", `DocumentsEndpoints.cs:18`) and the purge works (`DocumentService.cs:205-227`: deletes the image row, nulls `ocr_sealed`, marks `Purged`, audits counts) — **but no job runs it.** `RetentionWorker` only calls `SqlRetentionPurge` (idempotency 30 d, sessions 90 d; `SqlRetentionPurge.cs:23-27`); `PurgeIdCapturesRequest` is reachable only as a manual Owner/Manager command (`2101:11-12`), with the TODO at `DocumentService.cs:204` and HANDOFF line 326 ("nightly purge?") still open (A07-01). The guest ID numbers themselves (`gst.guest_id_secret`) and the guest profile have **no retention rule and no deletion/anonymisation command at all**; CA question **L2** (retention period, Form C) is open (A07-02). Idempotency results (which can hold names/phones, F-L03) are purged at 30 d — confirmed.

## (d) Owner's legal-risk note — plain English

> **Not legal advice.** This is an auditor's reading for the owner's decision. The CA/lawyer question **L1** (CA pack §7) is still open and must be answered before any real guest ID is stored.

**What HCC stores today.** For every guest you register, HCC keeps the **full ID number** (Aadhaar, passport, driving licence, voter ID, PAN or other) — encrypted with a key that lives only on the hotel PC — plus the ID type and the last 4 characters in clear for display. If the ID-photo feature is switched on later, it also keeps the photo and the name/date-of-birth read from it, encrypted, meant to be deleted after 90 days (today only when someone runs the purge). Nothing is deleted automatically; a guest's number stays as long as the guest profile exists.

**Who can see it.** Owner, Manager and Reception can press "Show ID"; each press is written to the audit trail (who, when, which guest — never the number). Cashier, Accountant, Housekeeping, Maintenance and Tech admin see "Restricted" or only the last 4. Technically, anyone who is an **Administrator on the hotel PC** can also decrypt every number (the key is bound to the PC, not to a person), and anyone who photographs or screenshots a phone while the dialog is open has the number. Backups contain only the encrypted form.

**Aadhaar Act 2016 and its regulations (my reading).** The Act restricts how Aadhaar numbers may be collected, stored, shared and displayed, and makes unauthorised use, sharing or disclosure of Aadhaar information an offence (sections 29, 37–38; penalties can include imprisonment). The Aadhaar (Sharing of Information) Regulations 2016 bar publishing or displaying Aadhaar numbers and require entities that hold them to protect them. UIDAI's public guidance for hotels and similar businesses is that they should **not keep a full copy of an Aadhaar number**; if a guest's Aadhaar is used as proof of identity, keep a **masked** copy (last four digits) at most, and under the 2021 offline-verification regulations an entity verifying an Aadhaar is not supposed to store the number. A hotel is not an authorised "requesting entity" for Aadhaar authentication; it is simply holding a document copy, which is exactly what the guidance tells it not to do in full. **So keeping full Aadhaar numbers is the thing HCC was told not to do, and the decision register (DEC-068) already records that it may be an offence.** Passport and other IDs are not under the Aadhaar Act, but see the next point.

**Digital Personal Data Protection Act 2023 (DPDP).** Once in force (the Rules were notified in 2025 with phased start dates — the lawyer should confirm which obligations already apply), a hotel is a "Data Fiduciary". It must give guests a clear **notice** and obtain **consent** (or rely on a stated lawful purpose such as a police guest register), collect **only what the purpose needs**, keep it **only as long as needed and then erase it**, apply **reasonable security safeguards**, and **report a personal-data breach** to the Data Protection Board and to the affected guests. Penalties go up to ₹250 crore for failing to protect data and ₹200 crore for breach-notification failures. A 12-digit Aadhaar number kept for years for every guest is high-value data under all of these headings.

**Why the hotel collects IDs at all.** Police/Sarai rules and the FRRO **Form C** for foreign guests do require a guest register with identity details (passport details for foreigners). That is a reason to *see and record* an ID — it is not a reason to keep full Aadhaar numbers indefinitely.

**What would reduce exposure (cheapest first).** 1) **Keep last-4 + ID type only** for Aadhaar (the code path exists: the README says "switch registration back to last 4 only and purge `gst.guest_id_secret`"; profiles saved with last-4 only already work). 2) Keep full numbers only for passports (needed for Form C) and treat Aadhaar as "last 4 + sighted". 3) If the owner still keeps full numbers: fix a **retention period** (e.g. a fixed number of days after departure), make the **purge automatic** (A07-01/02), add the **check-in notice/consent line**, put the key's offline copy and the "who may press Show ID" rule into a one-page written policy, and keep screenshots of the reveal dialog out of any report.

**The decision the owner must record (yes/no questions).** (i) Keep full Aadhaar numbers (against advice) — yes/no — and if yes, attach the lawyer's written answer to L1. (ii) Retention: delete ID numbers and images N days after departure — give N (or "never", with the reason). (iii) Who holds the offline key copy and where (safe), and who is allowed to press "Show ID". (iv) Whether the check-in form will show a data-protection notice before go-live. Until (i) is answered "yes, confirmed by the lawyer", the safest production setting is last-4 only.
