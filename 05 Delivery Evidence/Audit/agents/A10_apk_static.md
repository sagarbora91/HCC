## (b) Signing and keystore handling

- **Where the key lives.** Env `HCC_RELEASE_STORE_FILE`, `_STORE_PASSWORD`, `_KEY_ALIAS`, `_KEY_PASSWORD`, or `04 Android\android\keystore.properties`; password is never in `build.gradle` (`checkReleaseConfig` greps for `storePassword '...'`, `build-production.mjs:41`).
- **`hccSigningProblem` (`build.gradle:14-21`).** One string, set when: values missing; path not absolute or file missing; or the canonical path starts with the repo root (case-insensitive, junctions resolved by `canonicalPath`; repo root = `rootProject.projectDir.parentFile.parentFile`, which is the repo root). If it is set, `signingConfigs.hccRelease` is not even created, `productionRelease` gets no `signingConfig` (`:75`), and `preProductionReleaseBuild` depends on `checkHccReleaseSigning` (`:94-97`) which throws the string. Net: an unsigned or in-repo-keystore release APK cannot be produced through `assembleProductionRelease`. I read this, I did not run Gradle.
- **Tracked/ignored.** `04 Android\.gitignore` lines 13-17 ignore `android/keystore.properties`, `*.p12`, `*.key`, `*.jks`, `*.keystore`, `*.pfx`; root `.gitignore` ignores `*.apk`, `*.aab`, `*.jks`, `*.keystore`. `git check-ignore -v` confirms for `foo.jks`, `foo.keystore`, `foo.p12`, `foo.apk`, `android/keystore.properties`, the two APKs in the APK folder, and the generated `res/raw/hcc_hotel_ca.pem` and `assets/public/index.html`.
- **Nothing tracked.** `git ls-files` filtered by `apk|aab|jks|keystore|p12|pfx|key|pem|cer|crt|der|.env` returns one hit: `05 Delivery Evidence/Acceptance/defects/V9-1-debug-keystore-differs-no-inplace-upgrade-from-v8.md` (a markdown note, name only). A `find` of the whole repo tree (excluding `node_modules`) for `*.jks *.keystore keystore.properties *.p12 *.pfx` finds nothing. The 04 Android tracked files list has no key material.
- **No release APK in the evidence folder.** All six APKs in `05 Delivery Evidence\APK\` are debug-signed (`CN=Android Debug`) and debuggable (checked demo, server, v11; v8-v10 not opened but they are `-proto-debug-*` by name and git-ignored). The only `in.hcc.server` APK in existence is the Gradle output on disk, signed with a deleted throwaway key, bundling the throwaway CA. It cannot be handed out.
- **Debug key.** Debug builds use the Android Studio debug key of this PC; defect V9-1 (key differs between PCs, no in-place upgrade) is why the release key must be created once and backed up (README lines 54-58).
- **Leftovers outside the repo.** `%TEMP%\hccca\ca.key` and `ca.pem` (written 09:04 on 26 Oct, before the v12 run) still exist: a dev CA from an earlier compile-only check, not the v12 key (I looked at names and dates only, did not read the key). No `APK12*` or throwaway-keystore files were found in `%TEMP%`, consistent with the report's "deleted".

## (c) Token / PIN / device flow from code

Files: `03 Prototype\src\clients\sync\{auth,apk,instance,seal,cache,runtime}.ts`. APK mode = `isNative()`; browser build uses the cookie and is not covered here.

| Item | What the code does |
|---|---|
| Session token storage | `getAuth()` (`instance.ts:28-34`): `tokenAuth` over `sealedTokenStore(preferencesTokenStore(Preferences), wrapKey, 'session-token')`. Value stored = JSON `{token,userId,absoluteExpiresUtc,idleTimeoutSeconds,lastActivity}` sealed `hccs1.<iv>.<ct>`. If the Preferences plugin is missing it falls back to sealed `sessionStorage` (gone when Android closes the app). The three APKs all contain the Preferences plugin. |
| Sealing | AES-256-GCM, 12-byte random IV, AAD = `hcc-store\|<purpose>` (`auth.ts:104-116`, `seal.ts:36-48`). Unsealed values from an older build are read once and re-sealed (`auth.ts:110`). With no WebCrypto/IndexedDB key the value is stored **unsealed** (documented, `auth.ts:103`); inside the APK (https://localhost = secure context) that does not occur. |
| Wrapping key | `localWrapKey()` (`seal.ts:55-71`): non-extractable AES-256-GCM `CryptoKey` generated once and kept in the web view's IndexedDB `hcc-keys`/`keys`/`local-wrap-v1`. It lives in the same app data directory as the sealed values; README line 44 states the limit (no Android Keystore plugin). |
| Device id | `deviceId()` (`apk.ts:81-85`): `crypto.randomUUID()` (Math.random/Date fallback only without WebCrypto), plain in `localStorage hcc-device-id`, never cleared by sign-out or `forgetDevice`. Used only for the server label `<name> · <first 8 chars>` and the "this device" tag. It is **not** what is sent as `X-HCC-Device`. |
| `X-HCC-Device` | The header carries the **device token** returned once by the server's `RegisterDevice` command (`apk.ts` `registerThisDevice`), sent on every request, sign-in included (`auth.ts:61,148`). Stored sealed in Preferences key `hcc-device-token-sealed` (`instance.ts:23,36-37`), also held in a module variable for the synchronous header. Old plain `localStorage hcc-device-token` is migrated and deleted (`auth.ts:42-48`). Server side: `ValidateAsync(token, deviceToken)` refuses a PIN session unless the token is that of the device it was opened on (`AccessPorts.cs:147-150`, `HccComposition.cs:66`); password sessions ignore it. Spoofing needs the token, which the tablet only has sealed. I did not test the server side. |
| PIN roster (after F-L09) | `localStorage hcc-device-staff` = list of `{id, displayName}`. `id` = the login name sealed with an AES key derived by **HKDF-SHA256 from the device token** (`apk.ts:104-117`, purpose `hcc-roster-v1`, fixed salt `hcc-hkdf-v1`), random IV so the same name gets a different `id` each time. No login name is stored in clear. Display names are stored in clear. The login name is unsealed only at the moment of sign-in (`react.tsx` submit). If there is no device token the roster is deleted and not kept (`apk.ts saveStaff`). A foreign or forgotten registration cannot open the ids (pinned by `tests/sync-apk.mjs`: "a roster id cannot be opened with another registration key"). The review's "resolve login names server-side" is not done; sealing was chosen instead. |
| Read cache | IndexedDB `hcc-server-cache`, every slice sealed under a random per-sign-in data key; key wrapped (1) by PBKDF2-SHA256 (210,000 iterations, `cache.ts:22`) of the PIN or password and (2) by a random resume key kept in sealed Preferences `hcc-cache-resume`. Shown only after the server confirms the same user, or offline with a valid local session or a PIN/password re-entry; 5 wrong attempts wipe it (counter is stored in the lock record, `cache.ts:23`). Pinned by `tests/sync-cache-security.mjs`, `sync-foundation.mjs:199-200`. |
| Sign-out | `rt.signOut()` (`runtime.ts:391`): `POST /auth/sign-out` (errors swallowed), then `endSession()` -> `forget()` -> `wipeCache()` = clears the IndexedDB cache and the resume key and drops the in-memory slices. `tokenAuth.signOut` clears the stored token in a `finally`, so the token is removed locally even when the server call fails (the server session then lives until its idle/absolute expiry). 401 on a request that carried the token: token dropped (`auth.ts:166`) and `endSession`. Idle/absolute expiry by the lock record wipes the cache (`runtime.ts:375-385`). |
| What survives sign-out | Server address `hcc-server-url`, device token, device label, device id, staff roster (display names + sealed ids), wrapping key. By design: the tablet stays registered. **Also survives: every CSV/Excel/HTML file exported to the shared `Documents/HCC/` folder** (see A10-01). |
| Server-address change / "remove registration" | `signOut().finally(forgetDevice)`: deletes device token (sealed Preferences), label, roster (`react.tsx:186,201,212`; `apk.ts forgetDevice`). Device id is kept. The server keeps the device until it is revoked in Admin > Devices. |
| Uninstall | **Release** (`allowBackup=false` and rules excluding every domain): Preferences, IndexedDB (cache + wrapping key), localStorage are deleted with the app; nothing is restored on reinstall or on a new device; a reinstall gets a new device id and must be registered again, and the old registration should be revoked on the server. **Debug builds** (`allowBackup=true`, no rules): Android Auto Backup may restore Preferences and web view data after reinstall - not verified, needs a device. **Exported files in `Documents/HCC/`** are outside the app sandbox and on Android 10+ normally stay after uninstall - not verified, needs a device. |
| Per-request handling | Native HTTP via `CapacitorHttp` (`apk.ts capacitorFetch`, `instance.ts nativeFetch`), so the NSC applies. Only `https://` origins are accepted by `normaliseServerUrl` (userinfo, query, hash and paths refused). `probeServer` checks `product === 'Hotel Control Centre'` and `/system/health` before saving. |
