## Findings

1. **FIX: closing-records "Cash difference" is recomputed from two columns and differs from the stored record.** `08 Production/src/Hcc.Reporting/Reports/FxC/ClosingRecordsReport.cs` lines 32 and 44-45 compute `cash_counted_paise - cash_expected_paise` (0 when the count is NULL). Those columns are `Drawer.CountedPaise` / `Drawer.ExpectedPaise` of `DailyPackCalculator` (lines 211-226): expected and counted of the **last** shift of each till, and counted only when **every** till was counted. The record's own figure `figures.drawer.differencePaise` is the **sum of every closed shift's** counted - expected. They part when (a) a till had two shifts on the date (handover) and the earlier shift was short or over: e.g. morning shift short ₹100, evening shift balanced -> stored difference -₹100, this report 0; (b) one of two tills was counted with a difference and the other has no count: stored difference non-zero, this report 0 (count NULL). The production client today shows `differencePaise` from the record (`clients/sync/closing/figures.ts` line 58, `cash.difference: f.drawer.differencePaise`), so moving the report to the server changes the figure; and the prototype definition says "from the stored closing record". Right: take the difference from the record itself, e.g. deserialize `record_json` as `ClosingRecord` with `CanonicalJson.SerializerOptions` (as `ClosingService` line 379 does) and use `Figures.Drawer.DifferencePaise`, or `CAST(JSON_VALUE(s.record_json, '$.figures.drawer.differencePaise') AS BIGINT)` after checking the canonical property names. Net revenue and net receipts may stay on the columns (they equal the record). Add a SQL test whose `record_json` carries a two-shift drawer (one shift -10,000 paise, one 0) and expects -10,000; the current tests seed `record_json = N'[]'`, so they cannot see this.

2. **FIX: configuration history leaves out the Owner's GST rate changes.** `08 Production/src/Hcc.Reporting/Reports/FxC/ConfigHistoryReport.cs` lines 41-46 read `cfg.setting_change` only. On the server the dated GST master (Money and tax, Owner-only, DEC-069) is stored in `tax.gst_setting_version`, not in `cfg.setting_change`. The production client's `configHistory` slice, which the report reads in production today, is `historyFromServer(...)` **plus** `gstHistoryFromServer(...)` (`clients/sync/admin.ts` lines 283-287: the Owner GST versions, `source = 'owner'`, before = the previous version's value, after = the value with " (withdrawn)" when withdrawn); in the demo GST keys go through `SETTING_SET` and land in `s.configHistory` too. So the server report drops exactly the most sensitive configuration changes (rates of tax) that the prototype report lists. Right: union the Owner rows of `tax.gst_setting_version` for the property (`source = 'owner'`; seed / statutory rows stay out, as the client does) into the facts, with the same before / after display text as `gstHistoryFromServer` (`gstShow`; before "—" for the first version; " (withdrawn)" marker), actor from `changed_by`, effective from `effective_from`, reason; and a SQL test with one Owner GST version and one seed version (only the Owner one listed). Masters: neither side writes master changes into this history (the demo writes only settings handlers and meas-settings; production loads only setting + GST history), so "settings only, masters in the audit log" is a parity-neutral default; the title "Configuration and masters history" is inherited from the prototype.

Cheap improvement while fixing item 2: read `withdrawn_utc` and suffix " (withdrawn)" to `after`, as the client does for GST. DONE default 2 ("every stored change incl. a later withdrawn one is a row") is accurate but loses the information.
