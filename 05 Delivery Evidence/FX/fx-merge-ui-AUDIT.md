## Findings by question

**(a) Mock commands vs server.**
- Permission: `k.req('approve')`. In the demo grants only Owner and Manager hold it (`stream-rbac-matrix` pins `CUSTMERGE_*` to OWN MGR; the lane test refuses reception, cashier, accountant, supervisor and housekeeper with FORBIDDEN). On the server it is PERM-CRM-003 = OWN, MGR (3700 seed, no other grant anywhere). Not widened.
- Maker-checker: `proposedBy===uid` gives FORBIDDEN with the server's text. The checks run in the server's order: note length, NOT_FOUND, version (STALE_VERSION), status (INVALID_TRANSITION), checker (FORBIDDEN). Propose checks reason 5-300, NOT_FOUND, same key (VALIDATION), busy (INVALID_TRANSITION), as the server does. Idempotency is the generic `cmd.key` in `execute`.
- Copy-on-write: every write goes to `k.s`. The lane test and the probe confirm the input state is untouched.
- What moves: stays (through aliases), legacy stays (`customerIndex` reads the merged keys' legacy lookups too), preferences (same rule as `ApproveMergeAsync`: survivor kept, an empty one is copied, a different text becomes a note), guest notes (copied onto the survivor's guest; the server moves CRM notes). Not touched: the credit account (test), bookings, lines and receipts (probe: byte-identical), so invoices and posted money cannot change.
- Regression in `customers.ts`: when there are no aliases, `resolve` is the identity, `own === stays`, and the guest / latest / phone / e-mail / legacy choice gives the same result as before. The cache key adds `aliases` by identity (`undefined === undefined` for old saves). The probe confirms identical figures for non-merged customers. Other users of `customerIndex` (MEAS `repeat-loyalty`, `turnaway`, `meas-desk`, `PreferencesModal`) see the merged pair as one customer from then on. That is intended (counts only, no money).
- Transitive and cycles: approval re-points every alias whose target is the source (as the server's `UPDATE crm.customer_alias SET target_key=@t WHERE target_key=@s`), and `resolve` follows chains with a 20-step guard. A key that has been merged away is absent from `customerIndex`, so it can be neither source nor target of a new proposal, and an approval re-checks that both are still live. A cycle cannot form (probe).

## Notes (no change required in this lane)

- N1. The demo busy rule is stricter than the server's. The demo refuses a proposal when either customer is in any pending merge, and hides those pairs. The server refuses only a second pending merge with the same source, or a key that is already an alias. So for a group A, B, C with survivor B, the server accepts A→B and C→B pending together, and the demo accepts only one at a time. This narrows rather than widens, and is safe, but it should be listed under "Defaults used".
- N2. `CUSTMERGE_PROPOSE` / `DECIDE` call `customerIndex(k.s)` on the draft. That clones the whole `bookings` and `guests` slices, so both are rewritten to IndexedDB on each such command (probe: changed slices include `bookings`, `guests`). On FY26 that is a few MB per command, which is acceptable for a rare action. A related point: the `all` memo in `Customers.tsx` (lines 30, 149) lists `s.bookings, s.guests, s.date` but not `s.customerMergeX`. The list refreshes after a demo approval only because of that clone. Adding `s.customerMergeX` to both dependency lists would make it robust.
- N3. `moved.legacy` is always 0 because the handler calls `customerIndex` without the legacy lookup (probe output). It is not displayed anywhere. Fix it or drop the field when next touched.
- N4. The confirm's "all N stays" counts completed + legacy stays, while every booking of the merged-away key (upcoming and cancelled too) moves. This is only wording.
- N5. The production `proposedAt` / `decidedAt` keep the raw UTC string instead of `utcToClock(utc(...))` as the other mappers do. It is used only for sorting today.
- N6. The `_role-reads.json` rows are hand-written but consistent with the server. The gate's `RoleReadMatrixTests` must confirm them (DONE file).
- N7. The demo copies guest notes onto the survivor instead of moving them, and the prototype has no CRM tags, while the confirm names tags because the server moves them. The DONE file states both.
