## Findings

1. **FIX: expenses-cash tiles "Cash into drawer" / "Cash out of drawer" include hall and counter-bill cash; the prototype's do not.** `08 Production/src/Hcc.Reporting/Reports/CuA/ExpensesCashReport.cs` lines 40-41 and 75-76 sum every drawer movement of kind `payment` / `deposit` / `pos-sale` (in) and `refund` / `deposit-return` / `pos-void` (out). On the server those kinds are also written by hall receipts and hall cash refunds (`HallBillingCommands.CashAsync`, kind Payment / Refund, source `hall`), counter bills and their voids (`CounterBillService` lines 224 / 300, kind PosSale / PosVoid, source `counter-bill`), and the Udhaar desk payment (kind Payment, source `udhaar`). The prototype tile (`03 Prototype/src/domain/streams/closing.ts` reportPack, metrics `cash-in` / `cash-out`) is `RD(['payment','deposit'])` = folio receipts only, plus `udCash` (Udhaar), plus `posCash` = POS receipts only; hall receipts (`hallDrawerCash`) and counter bills (`lfCounterCash`) are not in it, before or after the trn-fix change (trn-fix put them in the drawer as kinds `hall-receipt` / `counter-bill`, which these tiles do not read). So a ₹5,000 cash hall advance adds ₹5,000 to the server tile and nothing to the prototype tile, same report id, same label. Udhaar is equivalent (both include it; an Udhaar reversal is a negative `payment` movement on both sides). Right: count only movements whose source is a folio receipt, Udhaar, or a POS bill (read `source_type` with the movements: `SqlCashBookSource` does not select it, so a small CuA query or an added column on the CuA side is needed; do not change `CashBookMovement` callers), and add a SQL test with one hall cash receipt and one counter cash bill that leaves both tiles unchanged. If the owner prefers the tile to mean "all cash into the drawer", that is a ruling for both sides (prototype tile and label), not a server-only change.

2. **Note: expenses-cash day rows for a past date that is not closed.** `ExpensesCashReport.cs` line 58 takes the cash-book day view, whose status for a past, unclosed date with drawer activity is `Past` (CashBookCalculator), with opening / expected / counted figures. The prototype `closingCash` shows `—` (or `Closed (no record)`) and blank figures for such a date, and `Past` is not one of its values. On a live server every past business date is closed (the date only advances by closing), so this arises only for imported or pre-HCC drawer rows. Also a closed date with no shift shows the carried opening and blank expected / counted (the prototype shows the closing record's figures). Acceptable; list both under Defaults in the DONE file.

3. **Note: figures are recomputed from the drawer, not read from the closing record.** expenses-cash (and cash-book) take opening / expected / counted / difference from `pay.shift` + `pay.cash_movement`, not from `cls.closing_snapshot` (the prototype reads `s.closings[d].cash`). Because the late-write barrier stops writes to a closed date, the two agree except on a reopened-and-corrected day before its re-close. The dateBasis text "from the closing record" is therefore loose on the server. No closing-snapshot SQL is involved in any of the four reports: daily-ops reads only `cls.business_day` (via `ClosedDatesAsync`), which the tests seed directly; that is the same table a real close writes first, so seeding it is a fair test of what the report reads. A reopened day keeps its `cls.business_day` row and shows `Closed` on the server (same as the existing `ReportingQueries`), while the prototype's reopen drops it from `closedDates`; pre-existing rule, not this lane.

4. **Note: cash-book sources and "is it cash".** The server cash book reads `pay.cash_movement` only, so vendor payments (source `vendor-payment`, kind expense), counter bills (`counter-bill`, pos-sale / pos-void), hall receipts (`hall`, payment / refund), Udhaar, staff advances, banking, till transfers and Owner drawings are all in it: equal to the trn-fix prototype drawer (`otherDrawerMovements`). The report itself never tests a method name for cash; the drawer movement is the test. (Whether a hall receipt reaches the drawer at this base depends on `HallBillingCommands.CashAsync` line 158 `method != "Cash"`: that literal is lane pay-b's fix, already on `claude/cu`, not this lane.) Status text `Closed` / `Open` / `Past` and the extra rows for unclosed past dates with activity are the server cash book page's own rules (the prototype lists only closing-record dates and today); same as `CashBookQueries`. Range totals foot: closing = last day's carried, over / short = Σ (carried − book), as `cbRange`. Signs: in / out columns positive, balance running, as the prototype.

5. **Note: expenses-cash split by the master.** `ExpensesCashReport.cs` lines 48-52: drawer = `PaymentMethodBook.SettlesToTill` (resolves the current name, the code, earlier names from the rename history, then the defaults): correct across a rename. Two small differences from the prototype: (a) "bank" on the server = every counted method that is neither till nor credit (an unknown / retired-unresolvable method lands in bank), while the prototype counts only methods whose settles-to is a bank account (an unknown method is in no tile, so its tiles need not add up); the server default is the better one, list it as a default (it is, in the DONE file). (b) "drawer" is decided by today's master, not by whether the expense actually made a drawer movement; if an Owner later changes a method's settles-to, old expenses move between tiles. Acceptable. Pending / rejected / void / draft expenses are out (`ExpenseRules.Counts` = Posted or Reversed, as `expenseCounts`); a reversal record is negative on its own date on both sides; capital purchases and their reversals are out on both sides (`Capital` flag incl. reversal of a capital original). ITC, petty-cash float and the month lock do not appear in the prototype definition and are correctly absent.
