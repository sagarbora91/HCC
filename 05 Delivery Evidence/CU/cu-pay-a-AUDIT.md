## Findings

1. **`03 Prototype/src/clients/sync/accounting.ts` lines 371, 373, 377, 378: the till test misses drawer cash that the server counts (regression for non-Owner approvers).** `mnyIsDrawer(state, e.method)` is an exact-key lookup in the drawer set (current name, code in capitals, earlier names from the rename history). The rename history is loaded only for users who may read it (PERM-MST-002, Owner; `clients/sync/money-master.ts` line 116). So a Manager approving or reversing an expense stored as `Cash` after the Owner renamed Cash to "Front till" gets `false` (probe: `mnyIsDrawer(s,'Cash') = false`, `folioIsDrawer(s,'Cash') = true`), sends no `tillId`, and the server, whose `PaymentMethodBook.SettlesToTill` resolves the stored text by name, code (upper-cased), earlier name, case-insensitive name and finally the literal "Cash", refuses with "Choose the till that pays this cash expense." / "Choose the till that takes this cash back." The base code sent the till for the literal "Cash", so this case worked before. No double count or missed movement is possible (the server alone decides the drawer movement from its master and ignores a `tillId` it does not need), but the approval is blocked and the cash slices do not reload. Right: decide the till as the server does, the AF2 way: use `folioIsDrawer` from `./money` (resolve through `mnyMethod`, then `mnyIsDrawer(row.name)`, else literal "Cash"), or an equivalent shared helper, at all four places. Add a test in `stream-cu-pay-a.mjs` with the renamed master and **no** history: expense method `Cash` and `cash` approve / reverse send `tillId` and reload `CASH_SLICES`.

2. **`03 Prototype/src/clients/sync/pos.ts` line 208: correct, keep.** `tender` is the master's current name after `mnyPick` (which resolves case, code and earlier name), and `mnyIsDrawer(current name)` hits the name key, so the till and the shift check follow "settles to a till" (DEC-052, DEC-MA-11a). The server `SettleCheck` matches the tender by **name** (then code, earlier name, case), not by id, re-resolves it with `Pick`, stores `method.Name` (the name at settle time) and decides the drawer itself; a stale client name still resolves there by its earlier name. Stored POS receipts and expenses keep their snapshot text after a rename (DEC-MA-3.2; the new tests show this for the in-memory handlers). No double count: one movement per settle, decided server-side.

3. **`03 Prototype/src/clients/sync/pos.ts` line 196 (note):** the missing-reference text stays "Enter the transaction reference." while the server (`Pick`) says "Enter the transaction reference for a non-cash payment." The DONE file lists this as a default and the pre-existing seeded test pins it; acceptable, but the brief asked for the same words as other callers. Owner / orchestrator may align later.

4. **(note, outside this lane) mock `services/mock/handlers/expenses.ts` line 111** refuses a retired funding source with "… — choose an active funding source.", while the server (`ExpenseRules` → `PaymentMethodBook.Pick`) and the new client precheck say "… — choose another payment method." Pre-existing divergence of the in-memory handler; not a lane defect.

5. **(note, outside this lane)** client-side drawer figures (`domain/streams/closing.ts`, `selectors.ts`) use `mnyIsDrawer` on stored text, so for a user without the rename history, receipts stored under an earlier name are not counted as drawer cash in the device's own cash book / expected-cash view. The server's shift close is unaffected. Same root cause as item 1; worth a shared resolver later.
