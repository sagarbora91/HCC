## Findings

1. **FIX - `03 Prototype/src/domain/streams/services.ts:91-92`**. The new branch lets Reception / Manager / Owner complete a front-desk wake-up because of the role name alone. It bypasses `can()`, which also checks `expiresOn`: an expired temporary user would pass, because the branch tests only `u.enabled`. With the stock grants the branch never runs, because these roles already hold `reservations` and line 90 returns first. So it matters only after an Owner has revoked the grant, and then the prototype allows what production refuses (`RequireWorkAsync` needs `PERM-GSV-002`). **Right:** remove the branch. The pre-existing `can(s,uid,'reservations')` already lets Reception, Manager and Owner do it, and stays in step with the server's `PERM-GSV-002` seed. Replace the F8 tests that strip `reservations` with: stock Reception / Manager / Owner can complete; Cashier is refused.
2. **FIX - `src/app/DeskAlerts.tsx:24`, `src/features/alerts/DeskAlertsPage.tsx:39`, `src/features/alerts/Mobile.tsx:24`**. The defect the training actually hit is still there. `RMD_FRONT_DESK_ROLES` (`reminders.ts:11`) shows the wake-up banner with a Done button to the Cashier, and both the prototype and the server refuse the Cashier with "housekeeping permission is required" / FORBIDDEN. Chapter 8 starts signed in as Priya (Cashier) (`06 Training/hcc-web/chapters_08.py:3`), which explains why the executor could not reproduce the refusal with Reception. This is pre-existing, but it is the F8 defect. **Right:** show the Done button (and Snooze, if the same applies) only when `gsvCanWork(s,uid,w)` is true. For a Cashier, show the banner read-only with "Ask Reception to make the call", or hide the wake-up rows. Add a test.
3. **FIX - `03 Prototype/tests/stream-cu-trn-fix.mjs:9-30`**. The F14 tests build the counter bill, hall receipts and vendor payment by editing state directly, so nothing proves the real commands create records these helpers read. **Right:** add at least one test that goes through `CTR_BILL_ISSUE` (Cash), `QUO_ACCEPT` + `HALL_ADVANCE_RECEIVE` (Cash and UPI) and `EXP_VENDOR_PAY` (Cash and Bank transfer). Add a case with the Cash method renamed through the payment-method master. Then assert `shiftExpected(s).expected === drawer(s)` and that `SHIFT_SUBMIT` with that figure closes the shift. The auditor's scratch version of this passes on d66a89e4, so this is a test gap, not a code fault.
4. NOTE - `src/clients/sync/hall.ts:75` maps the server state with `templates:[]`. Because of the F17 fallback, the **production** build's Templates tab and quotation preview now show the prototype's seeded "OWNER TO REPLACE" terms, even after the Owner has saved real terms on the server (the server still snapshots its own terms on SEND). Before this lane the list was empty. That was also wrong, but not misleading. **Follow-up (a later lane, not required of this one):** map the server's templates in the sync mapper, or limit the seeded fallback to the prototype build.
5. NOTE - `src/features/closing/Cashier.tsx:65`: "Other cash movements" is always drawn with "+". On a day when a counter bill is credited or a hall refund is paid with no matching receipt, `ex.other` is negative, so the page reads "+ -Rs x". The phone formula (`src/mobile/money/Cashier.tsx:28`) does not name vendor payments. Cosmetic.
6. NOTE - each source is one netted movement per day (for example, a hall advance less a refund is one line). The cash book's receipts and payments totals for those sources are net, not gross, and show no bill or event reference. The total is right. Gross lines would be better later.
7. NOTE - F19: CHM-F5's amount is unchanged after the party was cut from 3 to 2 adults. Harmless with fictional data. The FY26 re-pin sits on the same single lines that any later lane changing FY26 state must re-pin. If that happens, merge by re-running `stream-perf-store.mjs` / `stream-masters-fixture.mjs` and taking the new hash. No conflict exists today.
