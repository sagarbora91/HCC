## FIX list

1. **`Build-Installer.ps1` lines 226-228, 266, 296-313 - output folder left misleading after a failure.** The client exe is compiled straight into `-OutDir`; the old `SHA256SUMS.txt` is never removed at the start. If the server compile (or signing) then fails, `OutDir` holds a new client exe beside a `SHA256SUMS.txt` from the previous build of the same version, whose client hash no longer matches and whose server line names a file that was just deleted (line 303). With `-SignThumbprint`, a signtool failure (lines 300/306) leaves an unsigned exe in `OutDir` that looks like a finished build. **Right:** compile both setups into `<WorkDir>\out` (`/O` and `/DOutputDir` pointing there; `ClientSetupExe` from there), sign there, write `SHA256SUMS.txt` there, and only after all of that succeeds move the three files into `OutDir` (remove the old same-version files immediately before the move). Also delete a stale `<OutDir>\SHA256SUMS.txt` at the start of a real build, so a failed run never leaves a sums file that does not describe the folder.

2. **`Build-Installer.ps1` line 115 - `-LockScript` breaks under Windows PowerShell 5.1.** The command string contains embedded double quotes (line 283: `dotnet publish "<path with spaces>" ... -o "<path>"`); PowerShell 5.1 does not escape inner quotes when calling a native exe, so `Invoke-Serialized.ps1` receives `dotnet publish E:\Projects\HCC\...\08` and the rest as stray arguments (probe 2 above; the repo path always has spaces: `08 Production`, `Hotel Control Centre`). It fails loudly rather than silently, but rule 7 requires 5.1 and 7, and the DONE file's "tested on both" covers only the direct path. **Right:** write the command into a temporary `.ps1` under `<WorkDir>` and pass its path (`Invoke-Serialized.ps1` itself says "Long commands go in a .ps1 ... called by path"), or pass it with `-EncodedCommand`-style encoding; add the 5.1 lock path to the DONE results.

3. **`Build-Installer.ps1` lines 225, 269-270 and 209-211 - stale or foreign content swept into the installer.** `Hcc.iss` line 85 takes `{#PublishDir}\*` with `recursesubdirs` (excluding only `appsettings.Production*.json`), and line 101 takes `{#SqlMediaDir}\*` with `recursesubdirs`.
   - `-PublishDir` reuses any folder unchecked (only three files must exist). A folder the server was once run from can hold `logs\` (guest data), `appsettings.Development.json`, `certs\`, `*.pfx`, `Keys\`, `hcc-ops.json`: all of it would ship. **Right:** refuse a `-PublishDir` that contains any of `*.pfx`, `*.p12`, `*.key`, `*.pem`, `certs\`, `Keys\`, `logs\`, `hcc-ops.json`, `appsettings.*.json` other than `appsettings.json`; better, always copy the given folder into a freshly emptied `<WorkDir>\publish` through that filter.
   - The SQL staging cleanup (line 210) removes only stray top-level **files**; a stray sub-folder in `<WorkDir>\sqlmedia` survives and is shipped by the recursive glob. **Right:** remove `<WorkDir>\sqlmedia` entirely (it is inside the work folder) before staging, then copy the three files.
   - The hashes are checked on the source (line 198) but not on the staged copies (line 211). **Right:** hash the staged copies (or hash after copying instead of before), so what goes into the installer is exactly what the manifest names.
   The fresh publish path is fine: `<WorkDir>\publish` is deleted first and the delete is guarded to the work folder (line 279).

4. **`Build-Installer.ps1` lines 193, 202-204 - manifest absent is only a warning.** `sql-media.manifest.json` is now on `claude/inst` and shipped by `Hcc.iss` line 97, and `Bootstrap-HccSql.ps1` refuses media whose hash differs. A build without the manifest would produce an installer whose SQL step cannot pass. **Right:** a missing manifest is an error (`BUILD FAILED`) unless `-SkipSqlPayload`; keep the existing "no entry for X" error (correct) and the mismatch error (correct; the case-insensitive `-ne` against the lower-case manifest values works, verified by the dry run).

5. **`Build-Installer.ps1` (new) - no build provenance; this is also the fix for the lock-file finding (see (d)).** The build takes the working tree as it is: modified or untracked files ship (`Hcc.iss` line 86 takes every top-level `{#OpsDir}\*.ps1`, so a stray local helper script would be installed into `Operations\` on the hotel PC), the publish rewrites eight tracked `packages.lock.json` files, and nothing records which commit, SDK, runtime or Node built the installer. **Right:** (a) refuse to build when `git status --porcelain` is not empty (allow `-AllowDirty` for stub tests, printed as a warning); (b) build from a throw-away detached worktree of the gated commit (`git worktree add --detach <WorkDir>\src <commit>`, `npm ci`, build, publish, then `git worktree remove`), so the lock rewrite never touches a real checkout; (c) write `BUILDINFO.txt` beside `SHA256SUMS.txt` with the commit hash, `dotnet --version`, the `Microsoft.NETCore.App` / `Microsoft.AspNetCore.App` versions from `Hcc.Api.runtimeconfig.json` / `Hcc.Api.deps.json` of the publish, `node -v`, ISCC version, and "unsigned".

### (d) `packages.lock.json` churn - recommendation
- What happens: `RestorePackagesWithLockFile=true` without `RestoreLockedMode` (it is on only under `CI=true`; `HCC_RELEASE` does not set it). A `-r win-x64` restore adds a `net10.0/win-x64` target section to each lock file; the package versions of the existing graph stay as locked (central package management, exact versions), so the managed HCC and package assemblies are the same versions the gate tested. Only the lock files' text changes.
- Options:
  - `-p:RestorePackagesWithLockFile=false`: **reject**. It switches off the lock check altogether; nothing then proves the publish used the gated versions.
  - Committing RID-specific lock files alone: **not enough**. A lock with a `win-x64` section restored by the gate without a RID fails in locked mode; it needs `<RuntimeIdentifiers>win-x64</RuntimeIdentifiers>` in `Directory.Build.props` (a server build change: its own lane and an owner go under rule 4), then regenerated locks, then publish with `-p:RestoreLockedMode=true` so any drift fails the build.
  - Throw-away detached worktree / clean export of the gated commit: **recommended now** (FIX 5 b). It changes no server file, never dirties a real checkout, guarantees the installer is built from exactly the gated commit, and the lock rewrite is discarded with the worktree.
  - Longer term: add `RuntimeIdentifiers` + committed locks + locked-mode publish (own lane), which makes the gate and the publish restore the same graph.
- None of the options makes the shipped runtime identical to what the gate ran on: the gate runs framework-dependent on this PC's installed shared runtime; the self-contained publish bundles the runtime pack chosen by the SDK (latest patch it knows). Record both versions (FIX 5 c) and ideally run one smoke start of the published `Hcc.Api.exe` (for example the existing `migrate` plan / health path against a scratch database) as part of the orchestrator's real build.
