# Approval display and role-limit save fixes — 25 October 2026

## BL-01: approved discount displayed as Expired
Cause: folioApprovalExpired applied the expiry deadline to every Approved request, although discounts are posted immediately when approved. Fixed the shared selector so completed Approved discounts (including legacy records with no kind) remain Approved. Pending discounts and unused refund/company-credit authorizations still expire. No financial history or stored approval records were rewritten.

Regression: a real booking/check-in/charge/discount/approval sequence, followed by advancing the simulated clock beyond expiry, preserves Approved and the financial totals. Reapproval is rejected. Separate cases verify pending expiry and unexecuted versus executed refund/credit status.

## BL-02: unrelated limit change after editing a permission
Cause: permission/scope dropdowns submit immediately, but the generic Save button is attached to a separate limit form. Its initial value can be inherited from hotel settings; submitting that unchanged number created an explicit limit override and another policy/audit version. This was not a single permission command unexpectedly mutating both fields.

Added PolicyLimitEditor with a controlled value and a Save limit label. Unchanged effective values, blank/invalid values, fractional paise and out-of-range percentages cannot submit. A changed valid limit remains explicitly saveable, including zero. Role/effective-value changes reset the editor. Page instructions explain immediate submission and approval where required. No policy data was migrated and no existing audit records were removed.

Regression: server-rendered unchanged editor has a disabled Save limit button; numeric input validation cases; a real reservation-permission command preserves all limits and adds only its own audit/version; a subsequent explicit changed-limit command works and then becomes unchanged.
